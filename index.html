01 — Fondations

Vue d'ensemble

Deux forêts Active Directory indépendantes composent ce TP : LepalX.local pour le parc d'attractions Le Pal, construite sur un serveur avec interface graphique, et VetoX.local pour la clinique vétérinaire Soubagne, construite sur un Windows Server Core (sans interface graphique). Le bouton en haut de page bascule le contenu de chaque rubrique entre la marche à suivre graphique et la marche à suivre Core / PowerShell — seul ce qui a vraiment été fait dans ce TP est affiché ; le reste est signalé comme non réalisé plutôt qu'inventé.

Le vocabulaire de base

TermeCe que c'est
ForêtLe plus haut conteneur logique AD ; peut regrouper plusieurs domaines qui partagent un schéma et un catalogue global.
DomaineUne base d'annuaire avec ses propres comptes, groupes et stratégies (ici, une forêt = un domaine).
Contrôleur de domaine (DC)Le serveur qui héberge la base AD et répond aux authentifications.
OUUn conteneur d'organisation : classe les objets et sert de point d'ancrage pour GPO et délégation.
GroupeUn objet de sécurité qui porte des permissions et regroupe des comptes, indépendamment de leur OU.
GPOUn objet de stratégie de groupe : un ensemble de paramètres appliqués automatiquement aux comptes/ordinateurs d'un périmètre.
À retenirUne OU place un objet quelque part ; un groupe lui donne des droits ailleurs. Les deux notions sont indépendantes et se combinent.
02 — Fondations

Arborescence OU

✓ Graphique (LepalX)✓ Core / PowerShell (VetoX)

L'arborescence d'OU de LepalX reflète l'organisation réelle du parc : une direction et six pôles, chacun avec ses employés placés dans la sous-OU correspondante.

Graphique Créer une OU — Utilisateurs et ordinateurs AD

  1. Ouvrir dsa.msc (Utilisateurs et ordinateurs Active Directory) sur le contrôleur de domaine
  2. Clic droit sur le domaine (ou l'OU parente) → Nouveau → Unité d'organisation
  3. Saisir le nom (ex : OU_Direction)
  4. Laisser coché « Protéger le conteneur contre une suppression accidentelle »
  5. Valider, puis répéter pour chaque pôle et chaque sous-OU (Utilisateurs, Ordinateurs)

Core Créer une OU — PowerShell

New-ADOrganizationalUnit -Name "OU_Veterinaires" `
    -Path "DC=Veto6,DC=local" `
    -ProtectedFromAccidentalDeletion $true

New-ADOrganizationalUnit -Name "OU_Assistants" -Path "DC=Veto6,DC=local" -ProtectedFromAccidentalDeletion $true
New-ADOrganizationalUnit -Name "OU_Groupes"    -Path "DC=Veto6,DC=local" -ProtectedFromAccidentalDeletion $true

# Vérifier
Get-ADOrganizationalUnit -Filter * | Select-Object Name,DistinguishedName
Pourquoi -ProtectedFromAccidentalDeletionUne OU supprimée par erreur emporte tous ses objets et casse les GPO qui y étaient liées (elles deviennent orphelines dans SYSVOL). Ce paramètre bloque la suppression tant qu'il n'est pas explicitement levé.
03 — Fondations

Groupes AGDLP

✓ Graphique (LepalX)✓ Core / PowerShell (VetoX)

AGDLP est la méthode standard pour attribuer des permissions sans jamais mettre un compte utilisateur directement sur une ressource : Account → Global group → Domain Local group → Permission.

Graphique Créer un groupe — Utilisateurs et ordinateurs AD

  1. Clic droit sur l'OU cible (ex : OU_Groupes) → Nouveau → Groupe
  2. Nom du groupe (ex : GG_Direction)
  3. Étendue du groupe : Globale pour un GG, Domaine local pour un GDL
  4. Type de groupe : Sécurité
  5. Une fois créé, onglet Membres → Ajouter, pour y placer les comptes (dans un GG) ou d'autres groupes (dans un GDL)

Core Créer un groupe — PowerShell

New-ADGroup -Name "GG_Assistants" -GroupScope Global -GroupCategory Security `
    -Path "OU=OU_Groupes,DC=Veto6,DC=local"

Add-ADGroupMember -Identity "GG_Assistants" -Members "avial"

Pourquoi ne jamais court-circuiter la chaîne

  • Ajouter un compte directement sur une ACL de partage oblige à retoucher la ressource à chaque arrivée/départ.
  • Avec AGDLP, l'embauche ou le départ ne touche qu'une appartenance de groupe — la permission sur la ressource ne bouge jamais.
  • Un GG peut être membre de plusieurs GDL : un comité transverse (ex. GG_ComiteTechnique) s'imbrique dans les deux GG des pôles concernés.
04 — Fondations

Comptes utilisateurs

✓ PowerShell, pour les deux domaines (LepalX comme VetoX)

Les comptes sont créés par script à partir de l'organigramme, y compris sur LepalX qui a pourtant une interface graphique : avec ~70 employés à saisir, un script data-driven évite la saisie manuelle répétitive et reste reproductible. Ce contenu est donc identique quel que soit le mode sélectionné ci-dessus.

Le squelette du script

$Users = @(
    @{Prenom="Aurelie"; Nom="VIAL"; OU="OU=OU_Assistants,$DomainDN"; Groups=@("GG_Assistants","GG_Personnels")}
    # ... une ligne par employé
)

foreach ($u in $Users) {
    $sam = New-Sam -Prenom $u.Prenom -Nom $u.Nom
    New-ADUser -Name "$($u.Prenom) $($u.Nom)" -GivenName $u.Prenom -Surname $u.Nom `
        -SamAccountName $sam -Path $u.OU -AccountPassword $Password `
        -Enabled $true -ChangePasswordAtLogon $false
    foreach ($g in $u.Groups) { Add-ADGroupMember -Identity $g -Members $sam }
}
Piège rencontréDeux employés homonymes (même initiale + même nom, ex. Benoît et Bertrand SOUBAGNE) génèrent le même identifiant. Toujours vérifier les collisions avant de lancer un lot, ou rattraper à la main après coup avec un -SamAccountName différent.

Création rapide : une simple liste « Prénom Nom »

Version express, sans OU ni groupes à préparer : colle ta liste (un nom par ligne) et tous les comptes sont créés d'un coup. Par défaut ils vont dans le conteneur Users du domaine ; ils ne seront donc pas rangés dans la bonne OU, mais ils seront utilisables tout de suite. Fonctionne à l'identique en graphique et sur Server Core (ouvrir PowerShell, puis coller).

Import-Module ActiveDirectory
$Dom      = Get-ADDomain
$Domain   = $Dom.DNSRoot
$Path     = "CN=Users,$($Dom.DistinguishedName)"   # ou "OU=OU_Assistants,$($Dom.DistinguishedName)"
$Groupe   = ""                                      # ex : "GG_Assistants" (laisser vide = aucun groupe)
$Password = Read-Host -AsSecureString "Mot de passe initial des comptes"

$Texte = @"
Aurelie VIAL
Coralie BECOUZE
Benoit SOUBAGNE
Bertrand SOUBAGNE
"@
# Variante : $Texte = Get-Content C:\liste.txt -Raw

foreach ($ligne in ($Texte -split "`r?`n" | Where-Object { $_.Trim() })) {
    $prenom, $nom = $ligne.Trim() -split '\s+', 2

    # identifiant = initiale + nom, sans accents ni espaces (20 caractères max)
    $base = (($prenom.Substring(0,1) + $nom).Normalize('FormD') -replace '\p{Mn}', '').ToLower() -replace '[^a-z]', ''
    if ($base.Length -gt 18) { $base = $base.Substring(0,18) }

    # collision : bsoubagne, puis bsoubagne2, bsoubagne3...
    $sam = $base; $i = 2
    while (Get-ADUser -Filter "SamAccountName -eq '$sam'") { $sam = "$base$i"; $i++ }

    try {
        New-ADUser -Name "$prenom $nom" -GivenName $prenom -Surname $nom `
            -SamAccountName $sam -UserPrincipalName "$sam@$Domain" -Path $Path `
            -AccountPassword $Password -Enabled $true -ChangePasswordAtLogon $false
        if ($Groupe) { Add-ADGroupMember -Identity $Groupe -Members $sam }
        Write-Host "Créé : $prenom $nom  ->  $sam" -ForegroundColor Green
    } catch {
        Write-Warning "Échec pour $prenom $nom : $($_.Exception.Message)"
    }
}
À savoirLe mot de passe saisi doit respecter la politique du domaine (longueur, complexité), sinon chaque création échoue avec une erreur de mot de passe. Les collisions d'identifiant sont réglées automatiquement par un numéro. Pour déplacer ensuite des comptes dans la bonne OU : Move-ADObject -Identity "CN=Aurelie VIAL,CN=Users,DC=..." -TargetPath "OU=OU_Assistants,DC=...", ou glisser-déposer dans dsa.msc.

Restriction horaire (logonHours) — assistants vétérinaires

Pour les assistants, les horaires de connexion sont limités aux plages d'ouverture. L'attribut est un tableau de 21 octets (168 bits, un par heure de la semaine).

$heuresAutorisees = @{
    1 = (8..11) + (14..18)   # Lundi
    2 = (8..11) + (14..18)   # Mardi
    # ...
    6 = (8..11) + (14..15)   # Samedi
}
[byte[]]$logonHours = New-LogonHoursByteArray -AllowedHours $heuresAutorisees
Set-ADUser -Identity "avial" -Replace @{logonHours = $logonHours}
Erreur fréquente« L'attribut spécifié est déjà présent sur l'objet » signifie presque toujours que la variable n'est pas un vrai byte[] (souvent un Object[] généré sans typage explicite). Forcer le type avec [byte[]]$logonHours = ... résout le problème.
05 — Ressources & droits

Partages & NTFS

✓ Graphique (LepalX)✕ Non réalisé en Core dans ce TP

Deux couches de permissions s'appliquent à un dossier partagé accédé par le réseau : la permission de partage, et la permission NTFS sur le dossier lui-même.

Graphique Créer le partage et fixer les droits

  1. Créer le dossier (ex : C:\PartageAdmin) dans l'Explorateur
  2. Clic droit → Propriétés → onglet Partage → Partage avancé → cocher « Partager ce dossier »
  3. Bouton Autorisations : laisser « Utilisateurs authentifiés — Modification » (le vrai filtrage se fait côté NTFS)
  4. Onglet Sécurité → Modifier → Ajouter → saisir le groupe GDL concerné (ex : GDL_PartageAdmin_Modif)
  5. Cocher les cases de droits voulues (Modification / Lecture) puis valider
  6. Si un groupe hérité (ex : Utilisateurs) bloque une suppression : Paramètres avancés → Désactiver l'héritage → « Convertir en autorisations explicites », puis retirer le groupe

Core Statut

Non réalisé en CoreLes partages réseau de ce TP n'existaient que côté LepalX (serveur graphique). Aucun partage NTFS n'a été créé sur VetoX/Server Core dans cette session — cette rubrique ne présente donc pas de commandes PowerShell inventées pour New-SmbShare. Si le besoin se présente, la commande de base serait New-SmbShare -Name "Partage" -Path "C:\Partage" -FullAccess "GROUPE", à valider avant usage réel.

Qui pose quoi

  • Le partage (onglet Partage) est souvent laissé large : « Utilisateurs authentifiés — Modification ».
  • Le NTFS (onglet Sécurité) porte la granularité fine, via les groupes GDL — c'est lui qui fait le vrai travail de contrôle d'accès.
  • Un accès local (session ouverte sur le serveur) ignore la couche partage et ne voit que le NTFS.

07 — Stratégies & interdomaine

GPO

✓ Graphique (LepalX + VetoX via 2ᵉ DC graphique)✕ Non réalisé en Core pur dans ce TP

Une GPO se lie à un site, un domaine ou une OU. Plusieurs GPO peuvent s'appliquer en cascade à un même objet ; l'ordre détermine qui gagne en cas de conflit.

Les GPO du TP

  • GPO_EcranVeille (LepalX) — verrouillage automatique de session
  • GPO_BlocageRegedit (LepalX) — bloque regedit, avec exemption du groupe IT via filtrage de sécurité
  • GPO_AdminLocal (LepalX) — ajoute le groupe IT aux administrateurs locaux (Groupes restreints)
  • GPO_FondEcran (×2) (LepalX) — fond d'écran différent par pôle, via chemin UNC vers un partage
  • GPO_RaccourciWeb (VetoX) — raccourci vers le site de la clinique pour les assistants, créée depuis un second contrôleur de domaine graphique

Graphique Créer et lier une GPO — gpmc.msc

  1. Ouvrir gpmc.msc (Gestion de stratégie de groupe)
  2. Clic droit sur l'OU cible → Créer un objet GPO dans ce domaine, et le lier ici...
  3. Nommer la GPO, puis clic droit dessus → Modifier pour ouvrir l'éditeur
  4. Naviguer dans l'arborescence Ordinateur/Utilisateur → Stratégies ou Préférences selon le réglage voulu
  5. Pour un raccourci web (préférences) : Configuration utilisateur → Préférences → Paramètres Windows → Raccourcis → Nouveau → type URL

Filtrage de sécurité : exempter un groupe

  1. Sélectionner la GPO dans gpmc.msc → onglet Étendue
  2. Dans « Filtrage de sécurité », retirer « Utilisateurs authentifiés » et ajouter le groupe ciblé
  3. Pour exempter un sous-groupe qui hériterait quand même : onglet Délégation → Avancé → ajouter le groupe → cocher Refuser sur « Appliquer la stratégie de groupe »

Core Statut

Non réalisé en Core purCréer une GPO de registre simple est faisable en PowerShell (New-GPO, New-GPLink, Set-GPRegistryValue), mais le raccourci web repose sur les Préférences de stratégie de groupe (fichiers XML dans SYSVOL + GUID d'extension), difficiles à poser sans console graphique. Dans ce TP, la solution retenue a été de gérer les GPO de VetoX depuis un second contrôleur de domaine graphique du même domaine plutôt que d'écrire ces GPO à la main en PowerShell — voir la rubrique Server Core.

Diagnostiquer une GPO qui ne s'applique pas

gpupdate /force
gpresult /r
Retour d'expérienceUn « N/A » persistant dans gpresult n'est pas toujours un vrai blocage : vérifier aussi bêtement que la session a été fermée/rouverte, et que le dossier ciblé a été ouvert au moins une fois côté client.
08 — Stratégies & interdomaine

Server Core

✓ Core / PowerShell (VetoX) — section spécifique à ce mode

VetoX tourne sur un Windows Server sans interface graphique : toute l'administration passe par PowerShell. Cette rubrique n'a pas d'équivalent « Graphique » car son sujet est justement l'absence de GUI.

Premiers réflexes

# Entrer en session PowerShell depuis l'invite cmd par défaut
powershell

# Renommer puis redémarrer
Rename-Computer -NewName "SRV-VETO6" -Restart

# IP statique + DNS
New-NetIPAddress -InterfaceAlias "Ethernet0" -IPAddress 192.168.123.106 -PrefixLength 20 -DefaultGateway 192.168.112.1
Set-DnsClientServerAddress -InterfaceAlias "Ethernet0" -ServerAddresses 127.0.0.1

# Rôle AD DS puis promotion en forêt
Install-WindowsFeature AD-Domain-Services -IncludeManagementTools
Install-ADDSForest -DomainName "Veto6.local" -DomainNetbiosName "VETO6" -InstallDns:$true `
    -SafeModeAdministratorPassword (ConvertTo-SecureString "MotDePasse" -AsPlainText -Force) -Force:$true

Ce qui reste simple en PowerShell pur

  • Créer des OU, groupes, utilisateurs (New-ADOrganizationalUnit, New-ADGroup, New-ADUser)
  • Créer et lier une GPO basique (New-GPO, New-GPLink) une fois le module GroupPolicy chargé
  • Régler des valeurs de stratégie basées registre (Set-GPRegistryValue)

Ce qui devient pénible

Les préférences de stratégie de groupe (raccourcis, fichiers déposés) reposent sur des fichiers XML dans SYSVOL et des GUID d'extension à déclarer — pas de cmdlet haut niveau pour ça. La solution retenue dans ce TP : ajouter un second contrôleur de domaine avec interface graphique au même domaine VetoX, pour garder SRV-VETO6 conforme au sujet (Core) tout en disposant d'une console GPMC normale.

# Sur la nouvelle VM graphique, rejoindre le domaine existant en tant que DC additionnel
Install-ADDSDomainController -DomainName "Veto6.local" `
    -Credential (Get-Credential VETO6\Administrateur) -InstallDns:$true `
    -SafeModeAdministratorPassword (ConvertTo-SecureString "MotDePasse" -AsPlainText -Force) -Force:$true
Résolution DNS croiséePour que le DC graphique de VetoX et le DC de LepalX se voient (utile pour GPMC comme pour l'approbation), des redirecteurs conditionnels DNS ont été ajoutés des deux côtés — voir rubrique 09.

Activer le Bureau à distance (RDP) sur Core

# 1. Autoriser les connexions RDP (clé de registre)
Set-ItemProperty -Path 'HKLM:\System\CurrentControlSet\Control\Terminal Server' `
    -Name "fDenyTSConnections" -Value 0

# 2. Ouvrir le pare-feu pour le groupe "Bureau à distance"
Enable-NetFirewallRule -DisplayGroup "Remote Desktop"

# 3. (optionnel) Désactiver l'authentification au niveau réseau (NLA)
#    si le client ne supporte pas NLA correctement
Set-ItemProperty -Path 'HKLM:\System\CurrentControlSet\Control\Terminal Server\WinStations\RDP-Tcp' `
    -Name "UserAuthentication" -Value 0

# Vérifier l'état
(Get-ItemProperty -Path 'HKLM:\System\CurrentControlSet\Control\Terminal Server').fDenyTSConnections
Get-NetFirewallRule -DisplayGroup "Remote Desktop" | Select-Object DisplayName, Enabled
Pièges rencontrés
  • Set-ItemProperty sans -Name renvoie une erreur de paramètre manquant — les trois paramètres -Path, -Name et -Value sont obligatoires.
  • Enable-NetFirewallRule -DisplayGroup "Remote Desktop" échoue avec « groupe introuvable » si le nom du groupe n'est pas exact en anglais (pas de traduction) ou si le rôle Bureau à distance n'a jamais été touché : vérifier d'abord avec Get-NetFirewallRule -DisplayGroup "Remote Desktop".
  • Erreur côté client « correction d'oracle de chiffrement CredSSP » : c'est un décalage de version CredSSP entre le client (patché) et le serveur (non patché). Sur le serveur Core, forcer temporairement le niveau de compatibilité : 
    Set-ItemProperty -Path 'HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\System\CredSSP\Parameters' `
    -Name "AllowEncryptionOracle" -Value 2 -Type DWord -Force
    (2 = Vulnerable ; à revenir à 0 ou 1 une fois la mise à jour appliquée). Un redémarrage est parfois nécessaire pour que la clé soit prise en compte.
09 — Stratégies & interdomaine

Relation d'approbation

✓ Graphique (domain.msc sur le DC graphique de VetoX)✕ Non réalisé en Core pur dans ce TP

La confiance entre LepalX.local et VetoX.local permet à un compte d'un domaine d'accéder à des ressources de l'autre, sans dupliquer les comptes.

Prérequis technique : la résolution DNS (fait en PowerShell des deux côtés)

# Sur SRV-W2016-CELARIER
Add-DnsServerConditionalForwarderZone -Name "veto6.local" -MasterServers 192.168.123.106

# Sur le DC de VetoX
Add-DnsServerConditionalForwarderZone -Name "lepal6.local" -MasterServers 192.168.123.6

Graphique Créer l'approbation — domain.msc

  1. Ouvrir domain.msc (Domaines et approbations Active Directory) sur un DC graphique
  2. Clic droit sur le domaine → Propriétés → onglet Approbations → Nouvelle approbation
  3. Nom du domaine distant à approuver (ex : Veto6.local)
  4. Type : Externe · Sens : Bidirectionnelle
  5. Fournir les identifiants admin de l'autre domaine si demandé ; à l'étape « confirmer l'approbation entrante », Non suffit (elle a déjà été créée par l'assistant)
  6. Important : vérifier ensuite l'onglet Approbations sur les deux domaines. Si un sens n'apparaît que d'un côté, relancer l'assistant depuis le domaine manquant en choisissant « Cette approbation uniquement »
  7. Si la confiance ne semble pas prise en compte côté client : redémarrer le service Netlogon

Core Statut

Non réalisé en Core purUne relation d'approbation peut en théorie se créer en ligne de commande avec netdom trust, mais dans ce TP elle a été montée entièrement via l'assistant graphique domain.msc, sur un second contrôleur de domaine VetoX ajouté spécifiquement pour disposer d'une interface graphique (voir rubrique Server Core).

Vérifier que ça fonctionne

Sur les permissions NTFS d'un partage LepalX, ouvrir Ajouter → Emplacements : le domaine Veto6.local doit apparaître, et un compte comme avial doit être trouvable et ajoutable.
